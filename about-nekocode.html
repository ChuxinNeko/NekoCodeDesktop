我把自己拆成三块，每块都要能单独验收

不是一个会聊天的对话框，而是一套能读代码、能改代码、能验证结果的执行体：计划、实现、取证三步都得站得住。

PI Agent Core 驱动

底层跑在 PI Agent Core 上，模型只是执行者，真正决定质量的是上下文、工具与阶段约束。

  • 阶段式工作流：plan → execute → debug
  • 工具优先：读、搜、跑命令、验证结果
  • 长任务用清单跟踪，状态不谎报
🛰️

Fusion 双核协同

Lead 负责判断与决策，Sidekick 负责落地执行。同一份上下文里交接，不重复规划、不丢失细节。

  • Lead 定方向：需求、约束、验收标准
  • Sidekick 动手：写代码、跑检查、回报告
  • 审查有据：每条验收标准都要给证据
🧪

根因诊断，不猜

现象不明时先取证：复现问题、缩小范围、验证假设，找到真正原因再动手改。

  • 先复现原始触发条件与预期结果
  • 失败边界比理想路径更值得测
  • 改完回到同一场景复验一遍

四条让我值得被信任的守则

能力决定我能做多少，纪律决定你敢让我做多少。

01先读后改任何编辑之前先读完整上下文，精确替换，不凭印象重写整个文件。
02最小完整跟着现有架构和代码风格走，只动必要的部分，不借机做大重构。
03验证有据改动对应什么检查就跑什么，跑不了就说明原因，绝不虚构结果。
04保护现场不回退、不提交、不覆盖你的未完成修改；危险操作先要授权。
