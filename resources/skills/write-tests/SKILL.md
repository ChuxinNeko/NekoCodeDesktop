# 写测试

一个好测试的标准只有一条：**产品代码出错时它会失败，产品代码重构时它不会失败。**

不满足前半条的是摆设，不满足后半条的是负担。

## 先看现有测试怎么写

动手前必须做：

1. 找到同目录或同模块的测试文件，读两个完整用例。
2. 确认测试框架、运行命令、断言风格、mock 方式、fixture 放哪。
3. 新测试在命名和结构上跟着现有的走——测试文件的一致性比别出心裁重要。

运行命令通常在 `package.json` 的 `scripts.test`、`Makefile` 或 CI 配置里。**先把现有测试跑通**，再开始写；在一个本来就红的套件上加测试，你无法判断自己写对了没有。

## 挑用例：按"会不会出错"排序

不要从"这个函数有哪些分支"开始，从"这段代码最可能在哪里错"开始。

优先级从高到低：

1. **刚修过的缺陷** —— 先写一个能复现它的用例，确认在旧代码上失败。这是最有价值的测试。
2. **边界** —— 空输入、单元素、最大值、越界、恰好等于阈值的那个数。绝大多数缺陷藏在这里。
3. **错误路径** —— 输入非法时是否抛出预期的错误；失败后状态有没有被改坏。
4. **契约** —— 这个函数对外承诺了什么（返回值形状、是否修改入参、幂等性）。
5. **正常路径** —— 一个代表性的成功用例就够，不需要为多个相似输入各写一个。

跳过：语言本身保证的行为、简单的 getter/setter、只是转发调用的包装函数。

## 写法

**一个测试断言一件事。** 测试名说清断言的是什么行为，不是调用了什么函数：

- 好：`空数组返回 0 而不是抛异常`
- 差：`test sum function`

**按 准备 / 执行 / 断言 三段写**，中间空行隔开。准备部分超过五行就抽成工厂函数。

**断言行为，不断言实现**：

- 断言返回值、抛出的错误、写入的文件内容、最终状态。
- 不断言内部函数被调用了几次、私有字段的中间值——这些在重构时会误报。

**mock 越少越好**。只 mock 真正跨边界的东西：网络、时钟、随机数、文件系统（如果无法用临时目录）。能用真实对象就别 mock，被 mock 掉的代码是没有被测到的代码。

时间和随机数要注入或固定，否则测试会偶发失败。

## 验证测试本身有效

写完每个测试，做一次**变异检查**：把产品代码里对应的那行改错（改个比较符、去掉一个判断），确认测试变红，再改回来。

不会变红的测试是假的，删掉重写。

这一步对回归测试是必须的：修缺陷时，先写测试并确认它在未修复的代码上失败。

## 收尾

- 跑完整测试套件，不只是新增的那个文件——确认没有破坏别人。
- 测试必须可重复：不依赖执行顺序、不依赖上一条测试留下的状态、不依赖真实网络。
- 临时文件要在结束时清理，包括失败退出的路径。
- 报告时说明：加了哪些用例、各自覆盖什么风险、跑的结果。如果某个分支故意没测，说明原因。
