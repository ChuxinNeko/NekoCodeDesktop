# Fusion：双模型执行与验收

## 当前分工

- Lead 保持主会话：解释需求、提出调查问题、评估证据、设计、决策与最终审查，不实际展开调查。
- Sidekick 负责调查：代码定位、调用链梳理、根因调查、日志分析、资料检索与证据收集。代码调查用 `code_search`，其他只读调查用 `task(kind=explore)`；需要授权命令的复现使用有具体计划的 worker。Lead 收到证据后决定下一步，不把调查与修复决策混在一起。
- Sidekick 执行 Lead 的 `executionPlan`：文件编辑、编码、构建、测试；微小改动也必须委派。
- Lead 只保留协调工具和用于核实已知证据、审查改动的 `read`，不暴露搜索、目录遍历、网页/GitHub 调查、编辑、shell、SSH/远程桌面或任意插件执行工具。运行时工具门禁同步拒绝旧上下文中的直接调查及实施调用，不仅依赖提示词。
- 意图微妙、安全敏感的关键部分由 Lead 做判断并给出具体实施步骤，再由 Sidekick 落地。Sidekick 当前不能使用的执行工具应报告阻塞，不能让 Lead 绕过分工；该约束不扩大辅助会话权限。
- `code_search` 仍是一次性只读探索，不与实施会话混用。

## 第一步：持续上下文，逐任务权限

同一 Fusion 会话复用一个内存 Sidekick 会话，修正任务只需传递新增决策与反馈。每个任务独占该会话，重新绑定写范围、用户执行权限与取消信号；任务间关闭所有项目工具。仅拥有整个工作区的任务获得 shell，shell 不是文件沙箱。

取消、失败、关闭 Fusion、修改配置、更换父会话以及代码/历史恢复会使缓存会话失效。停止与切换会话等待辅助运行及退休清理。上下文只在当前桌面运行期保留，重启应用不会自动恢复一个有写权限的辅助任务。

## 第二步：结果与升级

辅助模型结束前调用 `fusion_report`，逐项覆盖计划中的原始验收条件：

- `completed`：实现可供审查；允许明确列出未验证项，不代表已验收。
- `blocked`：环境或工具阻塞。
- `needs_decision`：需要 Lead 补充设计/规格决定。
- `needs_escalation`：能力或正确性问题，需要 Lead 接管分析与决策，再给出可执行的修正计划。

未提供报告的运行不会被当作验收通过，结果标记为 `needs_decision`。普通测试失败不是自动升级理由；运行时不自动重派同一个失败任务。Lead 根据具体证据决定下一步，避免机械重试。

## 第三步：辅助用量归因

记录来源用户 entry、task ID、实际执行模型、请求来源 ID 和调用类别：推理、上下文压缩、缓存保温。保温费用归属写入缓存的请求，而不是随后新到来的用户消息。来源 ID 防止重复入账，历史分支检查防止挂到同时间戳的另一分支。

用量详情中可展开辅助任务/模型/类别明细。总体时长仍采用 Lead 墙钟跨度，不累加等待时间。保温复用 PI 自带的经济性判断，不新增固定频率的收费定时调用。

这些数字依据 SDK 提供的 usage，不是供应商账单：上游未报告的失败请求费用无法还原，摘要调用的模型标识按当时选择记录，未定价项不能当作免费。

## 第四步：保守压缩边界路由（默认关闭）

在 Fusion 选择器中开启“压缩时允许升档”，才允许 Sidekick 使用已选 Lead 模型。辅助模型通过 `fusion_request_upgrade` 提交具体正确性/能力风险与证据；运行时只在自然压缩成功后的、被等待的 SDK 边界考虑切换。没有压缩边界且无法安全推进时，报告 `needs_escalation` 交回 Lead，不主动制造压缩。

每个任务最多一次切换尝试（包含失败尝试）。后续没有升级请求的常规任务，可在下一个自然压缩边界回到已选 Sidekick。不会选择第三个模型、扩大工具权限或绕过用户验证限制。此版本是明确风险信号驱动的保守策略，不是训练过的任务分类器；它不承诺固定降本比例。

## 验证命令

```powershell
bun test ./test
bunx --no-install vitest run --config test/pi-fusion.vitest.config.ts
bun run pi:build
bun run typecheck
bun run build
```

SDK 专项使用独立配置，避免依赖本仓库没有带入的上游 `vitest.base.ts`。链路测试执行真实 SDK 工具循环和临时文件操作，外部模型输出被脚本化，不调用付费模型。实际缓存命中、费用收益、模型自我评估质量和可合并代码质量仍需真实任务对照实验。
